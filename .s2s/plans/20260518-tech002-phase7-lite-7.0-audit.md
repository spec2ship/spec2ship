### Drift analysis

**Drift D1 — `design` secondary lists `ADR-*` in SKILL.md, profile doesn't have it**

Root cause: `ADR-*` is a **Phase 3 output artifact** (Architecture Decision Record file written to `.s2s/decisions/`), not an in-session Phase 2 artifact embedded in `session.yaml.artifacts`. The profile only lists in-session artifact types. SKILL.md table conflates two categories.

**Resolution (7.1b)**: keep `ADR-*` in SKILL.md table but add inline clarification: `"ADR-* is a Phase 3 output artifact (written to .s2s/decisions/), not an in-session artifact"`. Alternative: remove ADR-* from this table (cleaner, but loses information). Recommend the clarification approach for human readability.

**Drift D2 — `brainstorm` secondary has `CONF` in profile, SKILL.md doesn't list it**

Root cause: `CONF` (conflicts) is a generic in-session artifact for ALL workflows when conflicts arise. The profile correctly includes it for brainstorm. SKILL.md omits it for brainstorm — likely an authoring oversight when the table was created.

**Resolution (7.1b)**: add `CONF` to SKILL.md `brainstorm` secondary list to match profile.

### 6.2 Triple-duplication: `templates/project/config.yaml`

`templates/project/config.yaml` is the user-facing project config template (copied during `/s2s:init`). It contains a `roundtable` section that DUPLICATES strategy/workflow mapping for a THIRD time:

| `roundtable.participants.by_workflow_type` (lines 65+) | `profiles/{workflow}.yaml.participants.default` + SKILL.md Workflow-Specific Defaults |

**Semantic distinction**: `config.yaml` is the USER'S runtime config (overrideable per project). The profile YAML is the plugin's DEFAULT that applies when user doesn't override. So they're not strict duplication; they're "defaults that should match" — but no enforcement.

**Phase 7-lite decision**: OUT OF SCOPE. Reasoning:
- Resolving this requires deciding whether config.yaml inherits from profile YAML (eliminating duplication) or stays standalone (preserving user override).
- That's an architectural decision that overlaps Phase 4 (roundtable.md master) and Phase 8 (thin launchers, where the config consumption mechanism might be re-evaluated).
- Phase 7-lite is documentation hardening; introducing config.yaml inheritance is not documentation.

**Action**: flag for Phase 4 plan §3 as part of the "Option A/B/C wiring decision" — config consumption pattern is part of the same decision space.
