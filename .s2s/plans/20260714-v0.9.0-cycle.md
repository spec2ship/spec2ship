## 1. Goal

Close the one workflow gap the Vektra dogfood proved costs real work: **nothing in s2s covers the transition from design to implementation**. After 6 design sessions Vektra had documents that captured the *what* and the *how* but not enough to start coding; the team ran 7 spec-completion steps and a custom consistency review **entirely outside s2s**, and that review found **3 blockers and 33 warnings in documents the workflow considered complete**.

The cycle ships `/s2s:review` — a pre-implementation consistency gate between `/s2s:design` and `/s2s:plan` — plus the four hygiene items that the pre-cycle re-triage surfaced.

**The gate is explicitly not a roundtable.** The decisions are already taken. It verifies that they are coherent, mutually consistent and implementable.

## 2. Non-goals

- **VKT-039 — validation/acceptance scenarios as a first-class artifact with coverage matrices.** In Vektra this was 48 scenarios / ~1300 lines. The critical review kept only VKT-037/038/069 as the genuine bridge; 039 is the Vektra-scale half. It stays parked in the `ideas.md` plan-integration umbrella. If it creeps into a PR, cut it.
- VKT-040 (import-boundary check), VKT-041 (decision resolution states), VKT-057, VKT-072 (roundtable sequencing guidance) — same umbrella.
- The dev-validator investment (QUAL-001's RES-RT-*, TEST-003's CTX-*): see §8.
- DEBT-002 (separate dev-tools repo): stays deferred to 1.0. BUG-027 is the cheap stopgap.

## 4. Hard constraint — read before designing FEAT-014

**s2s subagents report only to the caller and cannot talk to each other** (VKT-071).

The Vektra review that worked used **4 communicating agents**: the ref-checker finished first and broadcast its findings; the schema→api and api→schema tracers exchanged findings by DM; a lead consolidated and deduplicated. Cross-confirmation from two independent directions is what validated 2 of its 3 blockers. **That pattern is not expressible with s2s subagents.**

It must be re-expressed as **sequential orchestrator-mediated passes**: each pass returns findings to the orchestrator, which feeds pass N-1's output into pass N's input, and consolidates at the end (the orchestrator plays the lead's role). Do not design an agent team. Do not assume broadcast.

The second half of that lesson is why the gate is **three focused passes and not one big agent**: *"un singolo agente che legge 4000+ righe di specifiche tende a gravitare verso un tipo di problema alla volta."*

## 5. Design decisions (ADR-0013, to confirm before implementing)

Each carries a recommended answer. They are recommendations, not settled facts.

| # | Question | Recommended answer | Rationale |
|---|----------|-------------------|-----------|
| D1 | New command, or a gate inside `/s2s:plan`? | **New top-level `/s2s:review`** | It is not a roundtable, and it spans requirements + architecture + decisions, so it is not design-owned. Folding it into `plan.md` would make `plan` refuse to run on its own inputs. `plan` *consumes* the report instead. |
| D2 | Blocking or advisory? | **Advisory, escalating on BLOCKERs** | `/s2s:plan` warns and asks for confirmation when the latest report has open BLOCKER findings; it never hard-refuses. Matches "lean core + optional opt-in rigor", the principle gating the whole lean path. |
| D3 | Where do open questions live? | **Extend the existing `open_questions` artifacts** with `blocking: true\|false` and a resolution state | No new file, no new ID family. The gate reads what the roundtable already produces. |
| D4 | Incremental re-check after fixes? | **Yes — `--quick`, ref-checker pass only** | The source is explicit that a full re-review after fixes yields diminishing returns; the cheap ref-check is what you actually want in a fix loop. |
| D5 | Report format and location? | **`.s2s/reviews/{timestamp}-pre-impl-review.md`**, markdown with a findings table + YAML frontmatter carrying the counts and the input fingerprints | Markdown keeps it human-readable and reviewable in a PR; the frontmatter gives `/s2s:plan` something cheap to parse without reading the whole report. |
| D6 | How does `/s2s:plan` know the report is stale? | **Fingerprint the inputs** (sha256 of `requirements.md`, `architecture.md`, `decisions/*`) in the report frontmatter; `plan` warns "review is stale" when they differ | Without this, a report from before the last design session reads as a clean bill of health. This is the failure mode that makes an advisory gate actively harmful. |

D6 is the one worth arguing about. It is cheap and it is the difference between a gate and a rubber stamp.

## 6. Waves

Wave 0 is independent of everything else and can start immediately. Waves 1→3 are strictly sequential.

### Wave 0 — hygiene (no dependency on FEAT-014)

One PR. All four are small, and three of them are user-facing.

1. **BUG-027** — stop shipping dev tools.
   - First check whether the plugin manifest schema supports a path filter or exclude list. If it does, use it: zero build, zero CI surface. *This check gates the approach and has not been done — do it before writing anything.*
   - Otherwise add a release job in `.github/workflows/` publishing a stripped tree (drop `commands/dev/`, `agents/dev/`, `skills/dev-testing/`).
   - Verify: fresh `/plugin install` exposes no `/s2s:dev:*` command, no dev agent, no dev skill.
2. **BUG-008** — widen `commands/init.md` §5.4b from the `.s2s/local/`-only block to the full denylist (`sessions/`, `state.json`, `context-window.json`, `qa/`, `local/`). Keep the existing idempotent append/create logic; make the widening idempotent for projects initialized under TECH-013. Update the init completion banner (still says "local-only"). Align `s2s-guide/references/workspace.md`.
3. **BUG-028** — strip the authoring comments when rendering `templates/plan.md` in `commands/plan.md` (or move them out of the template into the command). Then decide per template whether the same comments in `templates/project/*` are a leak or legitimate user guidance — at `init` they are copied to the user, where a comment may be helpful rather than noise.
4. **hygiene** — `check-registry.md` documents `/s2s:dev:test --context`, which does not exist. Either mark it pending or remove it. Do not add the flag: it would run unimplemented checks.

### Wave 1 — FEAT-014 design

One PR. **ADR-0013** answering D1–D6 (§5), plus the report artifact schema (frontmatter fields, finding record, BLOCKER/WARNING/INFO taxonomy). Nothing else. This wave exists so the implementation is not designed inside a diff.

### Wave 2 — FEAT-014 implementation

One or two PRs. Three agents under `agents/validation/`, one command, one wiring change.

| Pass | Agent | Input | Finds |
|------|-------|-------|-------|
| 1 | ref-check | all artifacts | orphan and dangling refs across every ID family (REQ/ARCH/NFR/QS/SC/ADR/ERR/BR) |
| 2 | consistency | artifacts **+ pass 1 findings** | contradictions between `requirements.md`, `architecture.md` and the ADRs |
| 3 | implementability | artifacts **+ passes 1-2 findings** | blocking open questions, unresolved decisions, missing implementation contracts (the VKT-037 seven: schema, API contract, config reference…) |

The orchestrator consolidates, deduplicates, writes the report. Then: `/s2s:review` command (with `--quick` = pass 1 only), and `/s2s:plan` reads the latest report, checks the input fingerprints, surfaces open BLOCKERs and blocking OQs before generating tasks.

**Artifact-carrier rule — non-negotiable.** BUG-013 and BUG-026 both shipped a step that the runtime silently skipped because it had no artifact to prove it ran. Every gate here must leave a file behind: the report is the carrier for `/s2s:review`; for the `/s2s:plan` warning, persist `review_blockers: N` (and the report path) into the generated plan's frontmatter. A warning that exists only in the terminal will be skipped, and we already know it.

### Wave 3 — verification (dogfood exp51)

Per `skills/dev-testing/references/dogfood-e2e.md`. One fixture, seeded to make every gate fire:

| Seed | Verifies |

## 7. Risks

| Risk | Mitigation |
|------|-----------|
| **The gate ships and silently no-ops** — the BUG-013/BUG-026 failure class, and this cycle is nothing but gates | Artifact-carrier rule (§Wave 2). Wave 3 seeds each gate specifically. TECH-015 exists precisely because a gate we believed in was never fired. |
| **Scope creep toward VKT-039** | §2. The scenarios artifact is the visible-looking half. Cut it in review. |
| **Token cost**: 3 sequential passes over the full artifact set is heavy on a large project | `--quick`; pass agents receive the artifact set only, never the session transcript. Measure on the dogfood and record it in the baseline. |
| **The stale-report trap** (D6) | Input fingerprints. If D6 is rejected, the gate must not be advisory — an unfingerprinted advisory report is worse than no report. |
| **BUG-027's approach is unknown** until the manifest schema is checked | That check is the first task of Wave 0, not an implementation detail. |

## 9. Open questions for the user

1. **Dogfood mode for exp51** — *Recommended: user-drives*, the standing cadence. The v0.8.0 run was piloted by Claude via tmux as an explicit one-off exception; it worked, and the mechanics are now versioned in `dogfood-e2e.md`, so piloting again is a real option. But the standing rule is user-drives, and re-authorizing should be a deliberate choice, not drift.
2. **Does `/s2s:review` need its own `session:` lifecycle?** — *Recommended: no.* It is a one-shot analysis, not a multi-round deliberation. It reads artifacts, writes a report, exits. If it grows a lifecycle it has become a roundtable, which is precisely what §1 says it is not.
