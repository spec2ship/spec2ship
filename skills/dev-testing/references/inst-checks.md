# Instruction Quality Checks (INST-*)

Detailed definitions for instruction quality checks. These verify that command and agent files follow s2s patterns and guidelines.

---

## INST-001: Imperative Voice

| Property | Value |
|----------|-------|
| **Severity** | medium |
| **Target** | commands/*.md, commands/**/*.md |
| **Reference** | .claude/s2s-development.md → "Command Writing Patterns" |

### Purpose

Commands should use imperative voice for instructions. This makes instructions clearer and more actionable for Claude.

### Good Patterns

```markdown
Create the session file with...
Update the metrics after...
Display the results to the user
Read the configuration from...
```

### Bad Patterns

```markdown
The session file is created...        # Passive voice
You should update the metrics...      # Suggestion, not command
The results are displayed...          # Passive voice
Configuration should be read from...  # Suggestion
```

### Verification

1. Find all `## Instructions` sections in command files
2. Extract sentences that describe actions
3. Check if verbs are in imperative form (start with verb)
4. Flag passive voice and suggestion patterns

### Evidence Schema

```yaml
check: INST-001
status: pass | fail | warn
files_checked: 12
issues:
  - file: "commands/specs.md"
    line: 145
    text: "The session file is created"
    issue: "Passive voice"
    suggestion: "Create the session file"
```

## INST-002: Explicit Tool Usage

| Property | Value |
|----------|-------|
| **Severity** | high |
| **Target** | commands/*.md, commands/**/*.md |
| **Reference** | .claude/s2s-development.md → "Emphasis for Critical Instructions" |

### Purpose

Critical steps that involve tool calls should use explicit emphasis patterns. This ensures Claude executes the tool rather than just describing what should happen.

### Good Patterns

```markdown
**YOU MUST use Read tool NOW** to read the session file.
**Use the roundtable-facilitator agent** with this input:
**YOU MUST use Bash tool** to create the directory.
**Use the session-qa agent** with this input:
```

### Bad Patterns

```markdown
Read the session file.                # No emphasis
Call the facilitator agent.           # No "Use the X agent" pattern
Create the directory.                 # No tool mentioned
Run the validation.                   # Vague
```

### Verification

1. Find lines that should trigger tool calls:
   - File operations (read, write, edit)
   - Directory operations (mkdir, ls)
   - Agent invocations
2. Check for emphasis patterns:
   - `**YOU MUST use {Tool} tool**`
   - `**Use the {name} agent**`
3. Flag missing emphasis on critical operations

### Evidence Schema

```yaml
check: INST-002
status: pass | fail | warn
files_checked: 12
issues:
  - file: "commands/design.md"
    line: 230
    text: "Read the config file"
    issue: "Missing tool emphasis"
    suggestion: "**YOU MUST use Read tool** to read the config file"
```

## INST-003: No Ambiguity

| Property | Value |
|----------|-------|
| **Severity** | medium |
| **Target** | commands/*.md |
| **Reference** | .claude/s2s-development.md → "Prose Instructions vs Code Blocks" |

### Purpose

Steps should have clear success/failure criteria. Conditional logic should use explicit IF/ELSE branches.

### Good Patterns

```markdown
**IF** session file exists:
- Read the file
- Extract metrics

**ELSE**:
- Display error: "Session not found"
- Exit

**IF** rounds_completed > 0 AND agent_id exists:
- Resume with agent_id
**ELSE**:
- Start fresh
```

### Bad Patterns

```markdown
Read the file if needed.              # When is it "needed"?
Optionally update the metrics.        # When to do it?
You may want to check the status.     # Unclear if required
Handle errors appropriately.          # What's "appropriate"?
```

### Verification

1. Find conditional language ("if", "when", "optionally", "may")
2. Check for explicit branches (IF/ELSE structure)
3. Flag vague conditionals without clear criteria

### Evidence Schema

```yaml
check: INST-003
status: pass | fail | warn
files_checked: 12
issues:
  - file: "commands/brainstorm.md"
    line: 312
    text: "Read the file if needed"
    issue: "Ambiguous condition"
    suggestion: "IF file exists: Read the file. ELSE: Create new file."
```

## INST-004: Template Alignment

| Property | Value |
|----------|-------|
| **Severity** | medium |
| **Target** | commands/*.md vs templates/**/* |
| **Reference** | .claude/s2s-development.md → "Template-Based File Generation" |

### Purpose

YAML structures and content generated by commands should match the templates in `templates/`.

### Comparison Points

| Command Output | Template Source |
|----------------|-----------------|
| Session file structure | skills/roundtable-execution/references/session-schema.md |
| config-snapshot.yaml | templates/project/config.yaml (structure) |
| context-snapshot.yaml | templates/project/CONTEXT.md (structure) |

### Verification

1. Find YAML blocks in commands that represent file content
2. Compare structure with corresponding templates
3. Flag missing fields, extra fields, or structural differences

### Evidence Schema

```yaml
check: INST-004
status: pass | fail | warn
comparisons:
  - command: "commands/specs.md"
    template: "session-schema.md"
    status: pass
  - command: "commands/design.md"
    template: "session-schema.md"
    status: fail
    differences:
      - field: "metrics.tokens"
        issue: "Missing in command output"
```

## INST-005: Config Not Hardcoded

| Property | Value |
|----------|-------|
| **Severity** | high |
| **Target** | commands/*.md |
| **Reference** | .claude/s2s-development.md → "Config Priority", DEBT-001 |

### Purpose

Configuration values should come from config.yaml, not be hardcoded in commands.

### Good Patterns

```markdown
min_rounds: {from config-snapshot}
max_rounds: {from config-snapshot}
confidence_below: {from config}
```

### Bad Patterns

```markdown
min_rounds: 3                         # Hardcoded
min_rounds: {from config, default: 3} # Inline default
IF rounds < 3:                        # Magic number
max_rounds: 20                        # Hardcoded
```

### Values to Check

| Value | Expected Source |
|-------|-----------------|
| min_rounds | config.yaml → roundtable.limits.min_rounds |
| max_rounds | config.yaml → roundtable.limits.max_rounds |
| confidence_below | config.yaml → roundtable.escalation.triggers.confidence_below |
| max_rounds_per_conflict | config.yaml → roundtable.escalation.triggers.max_rounds_per_conflict |

### Verification

1. Search for numeric literals in command files
2. Check context: are they configuration values?
3. Flag hardcoded values that should come from config

### Evidence Schema

```yaml
check: INST-005
status: pass | fail | warn
files_checked: 12
issues:
  - file: "commands/specs.md"
    line: 456
    text: "IF rounds < 3:"
    issue: "Hardcoded min_rounds"
    suggestion: "IF rounds < {min_rounds from config}:"
```

## INST-006: ADR Compliance

| Property | Value |
|----------|-------|
| **Severity** | high |
| **Target** | commands/*.md, agents/**/*.md |
| **Reference** | .s2s/decisions/0010-artifact-state-model.md (ADR-0010) |

### Purpose

Artifact handling should follow ADR-0010: single `state` field instead of `status` + `agreement`.

### Good Patterns

```yaml
artifacts:
  requirements:
    REQ-001:
      state: "approved"           # Single state field
      created_round: 1
```

```markdown
Check artifact.state for current status.
Transition state from "draft" to "approved".
```

### Bad Patterns

```yaml
artifacts:
  requirements:
    REQ-001:
      status: "approved"          # OLD: separate status
      agreement: "consensus"      # OLD: separate agreement
```

```markdown
Check artifact.status and artifact.agreement.  # OLD pattern
```

### Valid States (per ADR-0010)

**Universal** (all types): draft, needs_discussion, in_progress, blocked, deferred, rejected

**Terminal by type**:
- REQ, BR, NFR, EX: approved, implemented
- ARCH, COMP: accepted
- IDEA: promoted, parked
- OQ, CONF: resolved

### Verification

1. Search for `status:` and `agreement:` in artifact contexts
2. Search for references to `artifact.status` or `artifact.agreement`
3. Verify `state:` field uses valid values
4. Flag non-compliant patterns

### Evidence Schema

```yaml
check: INST-006
status: pass | fail | warn
files_checked: 15
issues:
  - file: "commands/specs.md"
    line: 678
    text: "status: \"approved\""
    issue: "Using old status field instead of state"
    suggestion: "state: \"approved\""
  - file: "agents/roundtable/facilitator.md"
    line: 234
    text: "artifact.agreement"
    issue: "Referencing deprecated agreement field"
    suggestion: "Use artifact.state only"
```
