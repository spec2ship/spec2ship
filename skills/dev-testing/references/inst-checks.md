# Instruction Quality Checks (INST-*)

Detailed definitions for instruction quality checks. These verify that command and agent files follow s2s patterns and guidelines.

---

## INST-001: Imperative Voice

| Property | Value |
|----------|-------|
| **Severity** | medium |
| **Target** | commands/*.md, commands/**/*.md |
| **Reference** | .claude/s2s-development.md → "Command Writing Patterns" |

### Purpose

Commands should use imperative voice for instructions. This makes instructions clearer and more actionable for Claude.

### Good Patterns

```markdown
Create the session file with...
Update the metrics after...
Display the results to the user
Read the configuration from...
```

### Bad Patterns

```markdown
The session file is created...        # Passive voice
You should update the metrics...      # Suggestion, not command
The results are displayed...          # Passive voice
Configuration should be read from...  # Suggestion
```

### Verification

1. Find all `## Instructions` sections in command files
2. Extract sentences that describe actions
3. Check if verbs are in imperative form (start with verb)
4. Flag passive voice and suggestion patterns

### Evidence Schema

```yaml
check: INST-001
status: pass | fail | warn
files_checked: 12
issues:
  - file: "commands/specs.md"
    line: 145
    text: "The session file is created"
    issue: "Passive voice"
    suggestion: "Create the session file"
```

## INST-002: Explicit Tool Usage

| Property | Value |
|----------|-------|
| **Severity** | high |
| **Target** | commands/*.md, commands/**/*.md |
| **Reference** | .claude/s2s-development.md → "Emphasis for Critical Instructions" |

### Purpose

Critical steps that involve tool calls should use explicit emphasis patterns. This ensures Claude executes the tool rather than just describing what should happen.

### Good Patterns

```markdown
**YOU MUST use Read tool NOW** to read the session file.
**Use the roundtable-facilitator agent** with this input:
**YOU MUST use Bash tool** to create the directory.
**Use the session-qa agent** with this input:
```

### Bad Patterns

```markdown
Read the session file.                # No emphasis
Call the facilitator agent.           # No "Use the X agent" pattern
Create the directory.                 # No tool mentioned
Run the validation.                   # Vague
```

### Verification

1. Find lines that should trigger tool calls:
   - File operations (read, write, edit)
   - Directory operations (mkdir, ls)
   - Agent invocations
2. Check for emphasis patterns:
   - `**YOU MUST use {Tool} tool**`
   - `**Use the {name} agent**`
3. Flag missing emphasis on critical operations

### Evidence Schema

```yaml
check: INST-002
status: pass | fail | warn
files_checked: 12
issues:
  - file: "commands/design.md"
    line: 230
    text: "Read the config file"
    issue: "Missing tool emphasis"
    suggestion: "**YOU MUST use Read tool** to read the config file"
```

## INST-003: No Ambiguity

| Property | Value |
|----------|-------|
| **Severity** | medium |
| **Target** | commands/*.md |
| **Reference** | .claude/s2s-development.md → "Prose Instructions vs Code Blocks" |

### Purpose

Steps should have clear success/failure criteria. Conditional logic should use explicit IF/ELSE branches.

### Good Patterns

```markdown
**IF** session file exists:
- Read the file
- Extract metrics

**ELSE**:
- Display error: "Session not found"
- Exit

**IF** rounds_completed > 0 AND agent_id exists:
- Resume with agent_id
**ELSE**:
- Start fresh
```

### Bad Patterns

```markdown
Read the file if needed.              # When is it "needed"?
Optionally update the metrics.        # When to do it?
You may want to check the status.     # Unclear if required
Handle errors appropriately.          # What's "appropriate"?
```

### Verification

1. Find conditional language ("if", "when", "optionally", "may")
2. Check for explicit branches (IF/ELSE structure)
3. Flag vague conditionals without clear criteria

### Evidence Schema

```yaml
check: INST-003
status: pass | fail | warn
files_checked: 12
issues:
  - file: "commands/brainstorm.md"
    line: 312
    text: "Read the file if needed"
    issue: "Ambiguous condition"
    suggestion: "IF file exists: Read the file. ELSE: Create new file."
```

## INST-004: Template Alignment

| Property | Value |
|----------|-------|
| **Severity** | medium |
| **Target** | commands/*.md vs templates/**/* |
| **Reference** | .claude/s2s-development.md → "Template-Based File Generation" |

### Purpose

YAML structures and content generated by commands should match the templates in `templates/`.

### Comparison Points

| Command Output | Template Source |
|----------------|-----------------|
| Session file structure | skills/roundtable-execution/references/session-schema.md |
| config-snapshot.yaml | templates/project/config.yaml (structure) |
| context-snapshot.yaml | templates/project/CONTEXT.md (structure) |

### Verification

1. Find YAML blocks in commands that represent file content
2. Compare structure with corresponding templates
3. Flag missing fields, extra fields, or structural differences

### Evidence Schema

```yaml
check: INST-004
status: pass | fail | warn
comparisons:
  - command: "commands/specs.md"
    template: "session-schema.md"
    status: pass
  - command: "commands/design.md"
    template: "session-schema.md"
    status: fail
    differences:
      - field: "metrics.tokens"
        issue: "Missing in command output"
```

## INST-005: Config Not Hardcoded

| Property | Value |
|----------|-------|
| **Severity** | high |
| **Target** | commands/*.md |
| **Reference** | .claude/s2s-development.md → "Config Priority", DEBT-001 |

### Purpose

Configuration values should come from config.yaml, not be hardcoded in commands.

### Good Patterns

```markdown
min_rounds: {from config-snapshot}
max_rounds: {from config-snapshot}
confidence_below: {from config}
```

### Bad Patterns

```markdown
min_rounds: 3                         # Hardcoded
min_rounds: {from config, default: 3} # Inline default
IF rounds < 3:                        # Magic number
max_rounds: 20                        # Hardcoded
```

### Values to Check

| Value | Expected Source |
|-------|-----------------|
| min_rounds | config.yaml → roundtable.limits.min_rounds |
| max_rounds | config.yaml → roundtable.limits.max_rounds |
| confidence_below | config.yaml → roundtable.escalation.triggers.confidence_below |
| max_rounds_per_conflict | config.yaml → roundtable.escalation.triggers.max_rounds_per_conflict |

### Verification

1. Search for numeric literals in command files
2. Check context: are they configuration values?
3. Flag hardcoded values that should come from config

### Evidence Schema

```yaml
check: INST-005
status: pass | fail | warn
files_checked: 12
issues:
  - file: "commands/specs.md"
    line: 456
    text: "IF rounds < 3:"
    issue: "Hardcoded min_rounds"
    suggestion: "IF rounds < {min_rounds from config}:"
```

## INST-006: ADR Compliance

| Property | Value |
|----------|-------|
| **Severity** | high |
| **Target** | commands/*.md, agents/**/*.md |
| **Reference** | .s2s/decisions/0010-artifact-state-model.md (ADR-0010) |

### Purpose

Artifact handling should follow ADR-0010: single `state` field instead of `status` + `agreement`.

### Good Patterns

```yaml
artifacts:
  requirements:
    REQ-001:
      state: "approved"           # Single state field
      created_round: 1
```

```markdown
Check artifact.state for current status.
Transition state from "draft" to "approved".
```

### Bad Patterns

```yaml
artifacts:
  requirements:
    REQ-001:
      status: "approved"          # OLD: separate status
      agreement: "consensus"      # OLD: separate agreement
```

```markdown
Check artifact.status and artifact.agreement.  # OLD pattern
```

### Valid States (per ADR-0010)

**Universal** (all types): draft, needs_discussion, in_progress, blocked, deferred, rejected

**Terminal by type**:
- REQ, BR, NFR, EX: approved, implemented
- ARCH, COMP: accepted
- IDEA: promoted, parked
- OQ, CONF: resolved

### Verification

1. Search for `status:` and `agreement:` in artifact contexts
2. Search for references to `artifact.status` or `artifact.agreement`
3. Verify `state:` field uses valid values
4. Flag non-compliant patterns

### Evidence Schema

```yaml
check: INST-006
status: pass | fail | warn
files_checked: 15
issues:
  - file: "commands/specs.md"
    line: 678
    text: "status: \"approved\""
    issue: "Using old status field instead of state"
    suggestion: "state: \"approved\""
  - file: "agents/roundtable/facilitator.md"
    line: 234
    text: "artifact.agreement"
    issue: "Referencing deprecated agreement field"
    suggestion: "Use artifact.state only"
```

## INST-007: Frontmatter Completeness

| Property | Value |
|----------|-------|
| **Severity** | high |
| **Target** | commands/*.md, agents/**/*.md, skills/*/SKILL.md |
| **Reference** | .claude/CLAUDE.md → "Component Guidelines" |

### Purpose

Each component type has required frontmatter fields. Missing fields cause malfunctions or unexpected behavior.

### Required Fields by Type

| Component | Required | Optional |
|-----------|----------|----------|
| Commands | description, allowed-tools | argument-hint |
| Agents | name, description | model, color, tools |
| Skills | name, description, version | - |

### Good Patterns

**Command:**
```yaml
---
description: "Creates implementation plans from requirements"
allowed-tools: ["Read", "Write", "Glob", "Grep", "Bash", "Task", "AskUserQuestion"]
argument-hint: "<topic or --help>"
---
```

**Agent:**
```yaml
---
name: roundtable-facilitator
description: "Orchestrates roundtable discussions"
model: sonnet
tools: ["Read", "Write", "Glob", "Grep"]
---
```

**Skill:**
```yaml
---
name: arc42-templates
description: "This skill should be used when the user asks to..."
version: 0.1.0
---
```

### Bad Patterns

```yaml
---
description: "Does something"
# Missing allowed-tools for command!
---
```

```yaml
---
name: my-agent
# Missing description!
---
```

### Verification

1. Glob for all component files
2. Extract frontmatter (between `---` markers)
3. Parse YAML and check for required fields by type
4. Flag missing required fields

### Evidence Schema

```yaml
check: INST-007
status: pass | fail
files_checked: 25
issues:
  - file: "commands/example.md"
    type: "command"
    missing: ["allowed-tools"]
  - file: "skills/example/SKILL.md"
    type: "skill"
    missing: ["version"]
```

## INST-008: Subagent Spawning Prohibition

| Property | Value |
|----------|-------|
| **Severity** | critical |
| **Target** | agents/**/*.md |
| **Reference** | .claude/CLAUDE.md → "Key Reminders" #2 |

### Purpose

Agents cannot spawn other subagents. This is an architectural constraint. Orchestration must happen in commands, not agents.

### Anti-Patterns to Detect

```markdown
# In an agent file - ALL of these are WRONG:

**Use the roundtable-facilitator agent** with...
Task(subagent_type="s2s:roundtable:facilitator", ...)
Launch the technical-lead agent to...
Invoke the session-qa agent...
```

### Why This Matters

1. Agents run as subagents of Claude Code
2. Claude Code's Task tool is only available to the main agent
3. Subagents cannot invoke Task - it will silently fail or error
4. Orchestration belongs in commands

### Valid Patterns

Agents CAN mention other agents in documentation/explanations:
```markdown
Note: The facilitator agent will synthesize responses from participants.
```

But they CANNOT invoke them:
```markdown
**Use the facilitator agent** to synthesize...  # WRONG
```

### Verification

1. Read all agent files in `agents/`
2. Search for invocation patterns:
   - `**Use the * agent**`
   - `Task(subagent_type=`
   - `Launch the * agent`
   - `Invoke the * agent`
3. Distinguish documentation mentions from invocation attempts
4. Flag any invocation patterns

### Evidence Schema

```yaml
check: INST-008
status: pass | fail
files_checked: 12
issues:
  - file: "agents/roundtable/facilitator.md"
    line: 234
    text: "**Use the session-qa agent** to validate"
    issue: "Agent attempting to spawn subagent"
    fix: "Move orchestration to command file"
```

## INST-009: Skill Third Person Voice

| Property | Value |
|----------|-------|
| **Severity** | medium |
| **Target** | skills/*/SKILL.md |
| **Reference** | .claude/CLAUDE.md → "Component Guidelines" |

### Purpose

Skills use third person description ("This skill...") not first/second person. This is required for consistent trigger phrase detection.

### Good Patterns

```markdown
---
description: "This skill should be used when the user asks to..."
---

# My Skill

This skill provides patterns for...
```

### Bad Patterns

```markdown
---
description: "You should use this skill when..."  # Second person
---

# My Skill

I provide patterns for...  # First person
Use this skill when you...  # Second person imperative
```

### Verification

1. Read all SKILL.md files
2. Check description field for third person
3. Check first paragraph of body for third person
4. Flag first/second person usage

### Pattern Detection

| Pattern | Voice | Status |
|---------|-------|--------|
| "This skill should be used" | Third | OK |
| "This skill provides" | Third | OK |
| "You should use this" | Second | FLAG |
| "Use this skill when" | Second (imperative) | FLAG |
| "I provide" | First | FLAG |

### Evidence Schema

```yaml
check: INST-009
status: pass | fail | warn
files_checked: 15
issues:
  - file: "skills/example/SKILL.md"
    location: "description"
    text: "You should use this skill when..."
    issue: "Second person in description"
    suggestion: "This skill should be used when..."
```

## INST-010: Skill Progressive Disclosure

| Property | Value |
|----------|-------|
| **Severity** | medium |
| **Target** | skills/*/SKILL.md |
| **Reference** | .claude/s2s-development.md → "Adding New Skills" → "Progressive Disclosure" |

### Purpose

SKILL.md should be concise (overview + triggers). Detailed content belongs in `references/` folder. This prevents token bloat when skills are loaded.

### Guidelines

| Metric | Threshold | Action |
|--------|-----------|--------|
| SKILL.md words | < 1500 | OK |
| SKILL.md words | 1500-2000 | WARN |
| SKILL.md words | > 2000 | FAIL |

> Note: Guideline says "under 2,000 words" (s2s-development.md line 261)

### Good Pattern

```
skills/my-skill/
├── SKILL.md           # ~500 words: overview, triggers, references table
└── references/
    ├── detailed-guide.md
    ├── patterns.md
    └── examples.md
```

SKILL.md contains:
- Frontmatter
- Brief description
- When to use (triggers)
- References table pointing to detailed files

### Bad Pattern

```
skills/my-skill/
└── SKILL.md           # 3000+ words: everything inline
```

All content crammed into SKILL.md without references/ folder.

### Verification

1. For each skill, count words in SKILL.md
2. Check if references/ folder exists and has content
3. Flag oversized SKILL.md files
4. Suggest extraction to references/

### Evidence Schema

```yaml
check: INST-010
status: pass | warn | fail
files_checked: 15
issues:
  - file: "skills/example/SKILL.md"
    word_count: 2400
    threshold: 2000
    has_references: false
    issue: "SKILL.md exceeds 2000 words, no references folder"
    suggestion: "Extract detailed content to references/"
  - file: "skills/other/SKILL.md"
    word_count: 1700
    threshold: 2000
    has_references: true
    issue: "SKILL.md in warning zone (1500-2000)"
    suggestion: "Consider moving more content to references/"
```
